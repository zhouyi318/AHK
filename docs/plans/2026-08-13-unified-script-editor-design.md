# 统一脚本编辑器设计

## 背景

当前 GUI 以“窗口选择 / 进图脚本 / 存仓设置 / 运行控制”四个标签页组织，进图脚本编辑偏向录制器，存仓配置又是另一套独立表单。这样的结构在新增步骤类型、调整局部步骤、复用脚本能力时扩展成本较高，也不利于把 OCR、找图、鼠标、按键等能力统一纳入一个可编辑的脚本模型。

本次重构目标是把现有 GUI 升级为统一脚本编辑器：进图脚本与存仓流程脚本共用一套工作台，脚本由步骤组成，用户可以新建脚本、添加步骤、编辑某一步、保存脚本、试运行脚本，并支持从当前步骤运行和单步执行当前步骤。存仓原有的专用配置仍然保留，但执行流程改为可挂接脚本。

## 目标

- 提供统一脚本编辑器，而不是分别维护进图页和存仓页
- 支持脚本级管理：新建、保存、另存为、删除、启用停用
- 支持步骤级管理：添加、删除、复制、上下移动、启用停用、局部编辑
- 第一版同时支持基础执行类步骤与识别驱动类步骤
- 脚本流程支持线性执行与简单判断
- 支持整段试运行、从当前步骤运行、单步执行当前步骤
- 保持现有窗口绑定、OCR、找图、日志等基础能力可复用

## GUI 结构

新的 GUI 采用统一脚本编辑器工作台布局，替代现有“按业务拆页”的方式。

- 左侧：脚本列表
  - 展示所有脚本
  - 支持按脚本类型区分，例如 `enter_map`、`store_flow`
  - 支持新建、删除、复制、启用停用
- 中间：步骤列表
  - 展示当前脚本的所有步骤
  - 支持新增步骤、复制步骤、删除步骤、上下移动
  - 支持显示步骤是否启用、步骤类型、步骤摘要
  - 支持选中某一步作为“当前步骤”
- 右侧：步骤属性面板
  - 根据当前步骤类型切换对应的编辑表单
  - 编辑完成后直接同步到当前脚本缓冲区
- 顶部工具栏
  - 新建脚本、保存脚本、另存为、试运行、从当前步骤运行、单步执行当前步骤
- 底部状态区
  - 当前绑定窗口
  - 当前执行步骤
  - 运行日志和失败原因

存仓专用配置不消失，但从主编辑器中独立为辅助配置区域，包括：

- 存仓间隔分钟数
- 装备名称列表
- 关联存仓流程脚本

这样既保留现有存仓业务配置，又把流程动作纳入统一脚本系统。

## 脚本模型

脚本不再仅保存 `name + targetMapImage + steps`，而是升级为统一对象：

```json
{
  "id": "script_enter_map_001",
  "name": "祖玛进图",
  "type": "enter_map",
  "enabled": true,
  "metadata": {
    "targetMapImage": "zumap.bmp",
    "targetMapRegion": {"x1": 10, "y1": 20, "x2": 80, "y2": 60},
    "notes": ""
  },
  "steps": []
}
```

字段说明：

- `id`：脚本唯一标识，便于后续引用
- `name`：脚本名称
- `type`：脚本类型，第一版至少支持 `enter_map`、`store_flow`
- `enabled`：脚本是否启用
- `metadata`：脚本级附加信息
- `steps`：步骤数组

这样可以让进图脚本和存仓流程脚本共用一个存储体系，同时保留各自的脚本级附加属性。

## 步骤模型

每个步骤统一为以下结构：

```json
{
  "id": "step_001",
  "type": "click",
  "name": "点击进入按钮",
  "enabled": true,
  "params": {},
  "onSuccess": {"action": "next"},
  "onFailure": {"action": "stop"}
}
```

字段说明：

- `id`：步骤唯一标识
- `type`：步骤类型
- `name`：步骤显示名称，允许用户自定义
- `enabled`：是否启用该步骤
- `params`：该步骤的参数
- `onSuccess`：成功后的动作
- `onFailure`：失败后的动作

第一版流程控制只支持简单判断，不做完整流程图：

- `next`：进入下一步
- `stop`：停止执行
- `jump`：跳转到指定步骤

这能满足常见自动化场景，例如：

- OCR 命中则继续，否则停止
- 找图成功则继续，否则跳回某一步重试
- 图片点击失败则直接终止试运行

## 第一步支持的步骤类型

第一版同时支持基础执行类与识别驱动类步骤。

基础执行类：

- `click`：点击客户区坐标
- `wait`：等待指定毫秒数
- `keypress`：发送按键
- `mouse_move`：移动鼠标到指定位置
- `mouse_wheel`：执行滚轮动作

识别驱动类：

- `find_image`：在指定区域找图
- `click_image`：找到图片后直接点击
- `ocr_match`：OCR 识别并匹配目标文本

录制类能力不直接作为运行时步骤类型，而是作为步骤创建方式存在：

- 录制点击
- 录制按键
- 框选 OCR 区域
- 框选找图区域

这些录制结果会被转换成标准步骤对象，统一交给执行器处理。

## 步骤编辑体验

步骤编辑采用“步骤列表 + 右侧属性面板”模式。

- 中间步骤列表负责顺序管理
- 右侧属性面板负责详细参数编辑

不同步骤类型对应不同编辑表单：

- `click`
  - 坐标
  - 鼠标按钮
  - 点击前延时
- `wait`
  - 等待毫秒数
- `keypress`
  - 按键名
  - 是否组合键
  - 发送次数
- `mouse_move`
  - 坐标
  - 移动速度
- `mouse_wheel`
  - 方向
  - 滚动量
- `find_image`
  - 图片名
  - 搜索区域
  - 相似度
  - 超时时间
  - 成功/失败动作
- `click_image`
  - 图片名
  - 搜索区域
  - 相似度
  - 超时时间
  - 点击方式
- `ocr_match`
  - 搜索区域
  - 目标文本
  - 超时时间
  - 匹配模式
  - 成功/失败动作

交互重点：

- 用户可以直接选中“步骤 7”并只修改这一项
- 不再要求整段脚本重新录制
- 新增步骤时可从“空白创建”或“通过录制创建”两种路径进入

## 试运行与调试

第一版提供三种调试能力：

- `运行整个脚本`
- `从当前步骤开始运行`
- `单步执行当前步骤`

其中“单步执行当前步骤”是核心能力，适合快速验证：

- 当前 OCR 区域是否框对
- 当前图片是否能识别
- 当前点击坐标是否正确
- 当前按键是否符合预期

运行日志需要增强为步骤级日志，至少包含：

- 当前执行的脚本名
- 当前执行的步骤序号和步骤名
- 步骤执行结果
- 失败原因
- 是否发生跳转，以及跳转目标

这会比当前仅显示整体日志更适合调试简单判断流程。

## 模块拆分方案

建议将现有 `Main.ahk` 变薄，新增模块分层：

- `lib\ScriptEditor.ahk`
  - 统一脚本编辑器 GUI
  - 维护当前脚本、当前步骤、当前编辑状态
- `lib\ScriptRepository.ahk`
  - 统一脚本读写
  - 兼容旧脚本格式与新脚本格式
- `lib\StepSchema.ahk`
  - 维护步骤类型定义
  - 生成默认步骤对象
  - 校验步骤参数
- `lib\StepRunner.ahk`
  - 执行单个步骤或多个步骤
  - 处理 `onSuccess` / `onFailure`
- `lib\StepRecorders.ahk`
  - 管理录制点击、录制按键、区域选择等输入能力

现有模块复用策略：

- `Recorder.ahk`：保留其鼠标录制基础，逐步归并到 `StepRecorders`
- `Player.ahk`：保留点击、找图、坐标转换等底层能力，逐步归并到 `StepRunner`
- `TextRecognizer.ahk`：继续作为 OCR 服务模块使用
- `ScriptStore.ahk`：功能转移到 `ScriptRepository`，并负责兼容旧数据

## 兼容迁移策略

为了避免重构期间旧脚本不可用，迁移分三步进行。

### 阶段 1：新模型兼容读取

- 保留旧 JSON 文件位置
- 加载时自动识别旧结构
- 将旧结构映射为新脚本模型
- 保证现有进图脚本可以继续加载和执行

### 阶段 2：落统一编辑器

- 新 GUI 替换旧的进图脚本页
- 接入脚本列表、步骤列表、属性面板
- 支持新增、编辑、保存、运行、从当前步骤运行、单步运行

### 阶段 3：接入存仓业务

- 迁移存仓专用配置
- 支持关联存仓流程脚本
- 让 `Bot` 在到达存仓时机时执行该脚本

这样可以保证每个阶段都可运行，不会出现“大重构期间主流程不可用”的断层。

## 错误处理

统一脚本编辑器需要把错误区分为三类：

- 编辑时错误
  - 参数为空
  - 图片文件不存在
  - 区域无效
  - 跳转目标不存在
- 运行时错误
  - 绑定窗口不存在
  - 点击坐标越界
  - 找图超时
  - OCR 失败或未识别到文本
- 兼容性错误
  - 旧脚本字段缺失
  - 新旧字段映射失败

处理原则：

- 编辑时尽量前置校验，阻止保存无效步骤
- 运行时记录详细日志，不直接静默失败
- 单步执行失败时应明确显示失败原因和当前参数
- 脚本整体运行失败后保留当前步骤上下文，便于继续调试

## 测试策略

第一版至少需要覆盖以下测试：

- 脚本仓储测试
  - 新格式脚本保存/加载
  - 旧格式脚本兼容加载
- 步骤模型测试
  - 不同步骤类型默认值
  - 跳转目标合法性校验
- 执行器测试
  - 顺序执行
  - 成功继续
  - 失败停止
  - 失败跳转
  - 从当前步骤运行
  - 单步执行当前步骤
- GUI 回归测试
  - 新建脚本
  - 添加步骤
  - 修改步骤参数
  - 保存后重新加载

测试时继续遵循现有项目经验：

- OCR 坐标预期值要基于 `ResolveScreenRect` 或对应映射函数动态生成
- GUI 点击后的断言需保留足够等待时间，避免时序竞争

## 第一版边界

第一版明确不做以下内容：

- 完整流程图编辑器
- 多分支可视化连线
- 通用循环节点
- 远程同步脚本
- 多窗口并行执行

第一版聚焦于把“统一脚本编辑器 + 标准步骤模型 + 简单判断 + 单步调试”打稳。

## 结论

这次重构应以“统一脚本编辑器”为核心，而不是继续在现有标签页上叠加按钮。通过统一脚本模型、统一步骤模型、步骤属性面板、步骤级调试能力，以及完整的模块拆分和兼容迁移路径，可以把当前项目从“能录能回放”提升为“可编辑、可调试、可扩展”的自动化脚本平台。
